# 백업·복원 운영 체크리스트

> **범위:** Ubuntu + Docker Compose 기반 Mastodon의 일상적인 백업 준비와 복원 판단 기준입니다. 실험 중 실행한 세부 명령과 오류 수정 기록은 [Labs](../labs/README.md)에 따로 보관했습니다.

[핸드북 목차](../../README.md) · [독립 VM 복원 실험 기록](../labs/utm-disaster-recovery-v4.7.3.md)

## 무엇을 보존해야 하나?

| 대상 | 확인할 것 |
| --- | --- |
| PostgreSQL | 계정·게시물·관계·설정 등이 포함된 **일관성 있는 DB 백업** |
| 업로드 미디어 | 로컬 `public/system` 또는 실제 사용 중인 S3 호환 저장소 |
| 비밀 설정 | `.env.production`, DB 접속 및 암호화 키, Compose 오버라이드 등의 안전한 사본 |
| 환경 정보 | Mastodon 이미지 태그, DB 버전, 외부 스토리지·프록시 구성 |

Redis 캐시와 작업 큐, Elasticsearch 검색 인덱스는 PostgreSQL 덤프와 다르게 다뤄야 합니다. **DB 덤프만 있으면 완전한 복구가 된다고 생각하면 안 됩니다.**

## 백업을 만들기 전

- [ ] 데이터가 실제로 저장되는 볼륨·바인드 마운트·외부 저장소를 파악했다.
- [ ] DB와 미디어의 백업 시점이 어긋날 수 있음을 고려했다.
- [ ] 백업 원본은 암호화하고 암호·키는 분리 보관한다.
- [ ] 백업 보관 위치와 복사본의 접근 권한을 확인한다.
- [ ] 운영 서버 자체 손실에 대비한 별도 보관 장소가 있다.
- [ ] 자동 백업의 실패를 인지할 수 있는 확인 경로가 있다.

## 백업 후 최소 확인

- [ ] 백업 파일이 실제 존재하며 크기가 비정상적으로 작지 않다.
- [ ] 전송 전후 SHA-256 등으로 파일 무결성을 대조했다.
- [ ] 암호화했다면 안전한 환경에서 복호화가 가능한지 확인했다.
- [ ] DB 덤프의 형식과 미디어 파일·설정 자료의 존재를 확인했다.
- [ ] **복원이 실제로 가능했는지**와 **아직 실험하지 못한 범위**를 구별해 기록했다.

백업 파일 검사에 통과한 것과 Web 로그인까지 가능한 복원을 확인한 것은 **서로 다른 단계**입니다. 처음부터 네 개의 VM을 만들거나 모든 실험 체크포인트를 따라 할 필요는 없습니다. 여유가 있을 때 현재 운영 환경과 격리된 대상에서 대표적인 복구를 확인하면 됩니다.

## 사고가 났을 때

1. 데이터 손실·암호화 키 교체·마이그레이션 등 **되돌릴 수 없는 조치는 중지**합니다.
2. 장애 시점과 마지막 정상 백업의 시점을 확인합니다.
3. 새 대상에 DB·미디어·비밀 설정을 함께 복원하고, 원본 서버와 외부로 동시에 연합하지 않도록 격리 범위를 정합니다.
4. Web 응답과 계정·미디어 조회로 주요 기능을 확인하고, 외부 연동은 준비한 뒤 순차적으로 복구합니다.

이 단계는 **판단 순서**이지 모든 구성에 적용 가능한 즉시 실행 스크립트가 아닙니다. 구체적인 복구 방법은 사용 중인 Mastodon 릴리스·DB·객체 저장소 구성에 따라 달라집니다.
