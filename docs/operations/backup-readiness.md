# 백업·복원 운영 체크리스트

> **범위:** Ubuntu + Docker Compose 기반 Mastodon의 일상적인 백업 준비와 복원 판단 기준입니다. 실험 중 실행한 세부 명령과 오류 수정 기록은 [Labs](../labs/README.md)에 따로 보관했습니다.

[핸드북 목차](../handbook-index.md) · [독립 VM 복원 실험 기록](../labs/utm-disaster-recovery-v4.7.3.md)

## 무엇을 보존해야 하나?

| 대상 | 확인할 것 |
| --- | --- |
| PostgreSQL | 계정·게시물·관계·설정 등이 포함된 **일관성 있는 DB 백업** |
| 업로드 미디어 | 로컬 `public/system` 또는 실제 사용 중인 S3 호환 저장소 |
| 비밀 설정 | `.env.production`, DB 접속 및 암호화 키, Compose 오버라이드 등의 안전한 사본 |
| 환경 정보 | Mastodon 이미지 태그, DB 버전, 외부 스토리지·프록시 구성 |

Redis 캐시와 작업 큐, Elasticsearch 검색 인덱스는 PostgreSQL 덤프와 다르게 다뤄야 합니다. **DB 덤프만 있으면 완전한 복구가 된다고 생각하면 안 됩니다.**

## 백업을 만들기 전

- [ ] 데이터가 실제로 저장되는 볼륨·바인드 마운트·외부 저장소를 파악했다.
- [ ] DB와 미디어의 백업 시점이 어긋날 수 있음을 고려했다.
- [ ] 백업 원본은 암호화하고 암호·키는 분리 보관한다.
- [ ] 백업 보관 위치와 복사본의 접근 권한을 확인한다.
- [ ] 운영 서버 자체 손실에 대비한 별도 보관 장소가 있다.
- [ ] 자동 백업의 실패를 인지할 수 있는 확인 경로가 있다.
- [ ] 업로드 실패 시 로컬 백업을 보존하며, 정기 업로드가 실제로 성공하기 전에는 새 보관 위치에 자동 삭제를 적용하지 않는다.

## 백업 후 최소 확인

- [ ] 백업 파일이 실제 존재하며 크기가 비정상적으로 작지 않다.
- [ ] 전송 전후 SHA-256 등으로 파일 무결성을 대조했다.
- [ ] 암호화했다면 안전한 환경에서 복호화가 가능한지 확인했다.
- [ ] DB 덤프의 형식과 미디어 파일·설정 자료의 존재를 확인했다.
- [ ] **복원이 실제로 가능했는지**와 **아직 실험하지 못한 범위**를 구별해 기록했다.

백업 파일 검사에 통과한 것과 Web 로그인까지 가능한 복원을 확인한 것은 **서로 다른 단계**입니다. 처음부터 네 개의 VM을 만들거나 모든 실험 체크포인트를 따라 할 필요는 없습니다. 여유가 있을 때 현재 운영 환경과 격리된 대상에서 대표적인 복구를 확인하면 됩니다.

## 운영 사례: R2 백업 저장소 분리와 7일 순환 보관 (2026-11-15~18)

이 사례는 **단계적 이관 → 실제 자동 실행 확인 → 보관 정책 활성화** 순서의 필요성을 보여줍니다.

1. 운영 중인 미디어 버킷과 별도로 **비공개 DB 백업 버킷**을 마련하고, 미디어·백업 API 토큰을 버킷별로 제한했습니다. 이전에 전체 버킷 관리자 권한이 있던 토큰은 신규 인증정보의 실제 미디어 업로드·조회가 작동한 뒤 폐기했습니다.
2. 기존 백업 일곱 개는 원본을 지우지 않고 새 버킷으로 **복사**했습니다. 파일명과 크기는 대조했지만, 해시 일치 또는 실제 복원 성공까지 입증한 것은 아닙니다.
3. 새 대상으로의 첫 정기 백업은 접근 거부(403)로 실패했습니다. 실패 시 로컬 압축파일을 남기도록 해 둔 상태에서 권한 확인 동작을 조정하고, 당시 압축파일을 수동 업로드했습니다.
4. 이후 **11월 17일과 18일** 정기 실행으로 새 버킷 업로드가 이루어졌습니다. 일시적 501 오류가 발생했지만 재시도로 성공했습니다.
5. 11월 17일에 **7일 보관 정책을 복구**하고, 18일 신규 버킷에서 최신 7개 백업만 남은 것을 확인했습니다. 수정 시각 기반의 나이 판단과 업로드 성공 후 삭제 순서가 중요합니다.
6. 옛 미디어 버킷의 백업 원본 일곱 개는 일단 보존했습니다. 원본에는 민감한 설정이 포함될 수 있으므로 오래된 저장 위치의 **공개 접근 가능성**과 별도 폐기 조건을 신중히 다뤄야 합니다.

**자동 업로드 성공, 보관 정책 실행, 복원 검증은 서로 다른 완료 단계입니다.** 또한 비공개 버킷과 최소 권한 토큰은 파일 암호화를 대체하지 않습니다. 당시 운영 DB 백업은 암호화하지 않았고, 암호화 및 전체 복원 검증은 **별도 보류 과제**로 남겨 두었습니다.

자세한 오류와 시점별 증거는 [2026-11-15~18 머스타드 R2 운영 기록](https://github.com/thanksstevenkim/mastodon-lab/blob/main/operations/cloudflare-r2-backup-isolation-and-credential-rotation-2026-11-16.md)에 따로 보관합니다. 위 사례의 설정값이나 토큰을 그대로 복사해 적용하는 절차는 아닙니다.

## 사고가 났을 때

1. 데이터 손실·암호화 키 교체·마이그레이션 등 **되돌릴 수 없는 조치는 중지**합니다.
2. 장애 시점과 마지막 정상 백업의 시점을 확인합니다.
3. 새 대상에 DB·미디어·비밀 설정을 함께 복원하고, 원본 서버와 외부로 동시에 연합하지 않도록 격리 범위를 정합니다.
4. Web 응답과 계정·미디어 조회로 주요 기능을 확인하고, 외부 연동은 준비한 뒤 순차적으로 복구합니다.

이 단계는 **판단 순서**이지 모든 구성에 적용 가능한 즉시 실행 스크립트가 아닙니다. 구체적인 복구 방법은 사용 중인 Mastodon 릴리스·DB·객체 저장소 구성에 따라 달라집니다.
