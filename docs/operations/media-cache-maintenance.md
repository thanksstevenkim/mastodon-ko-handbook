# 원격 미디어 캐시 정리와 객체 저장소 관리

> **범위:** Mastodon에서 다른 서버의 이미지를 임시로 보관한 **원격 미디어 캐시** 관리입니다. 로컬 이용자가 업로드한 미디어, PostgreSQL 백업, Elasticsearch 스냅샷과 혼동하지 마세요. 대규모 객체 삭제 스크립트나 특정 R2 버킷 경로를 그대로 복제하는 매뉴얼이 아닙니다.

## 무엇을 지울 수 있고, 무엇을 보존해야 하나?

| 대상 | 판단 |
| --- | --- |
| 로컬 이용자가 업로드한 미디어 | 원격 캐시 정리 대상 **아님** |
| 다른 서버에서 캐시한 게시물 첨부파일 | 일정 기간이 지난 것부터 정리 후보 |
| 원격 계정 아바타·헤더 | 게시물 첨부파일과 다른 관리 옵션; 별도 판단 |
| DB가 참조하는 R2 객체 | 삭제 전 참조·키 구조를 반드시 고려 |
| Elasticsearch 백업·스냅샷 | 미디어 캐시 정리와 완전히 별개 |

원격 캐시가 지워졌다고 원본 서버의 게시물이 삭제된 것은 아닙니다. 다만 원격 서버에서 다시 가져올 수 없거나 URL이 바뀐 경우 **미디어가 표시되지 않을 수 있으므로**, 무조건 재생성 가능하다고 단정하지 마세요.

## 1. 먼저 도움말과 Dry Run

Mastodon이 실행 중인 **Compose 프로젝트 디렉터리**에서 현재 버전의 옵션을 확인합니다.

```bash
docker compose exec -T web bin/tootctl media remove --help
```

예를 들어, 원격 첨부파일 정리 후보를 30일 기준·동시 처리 2로 살펴보려면:

```bash
docker compose exec -T web bin/tootctl media remove \
  --days 30 --concurrency 2 --dry-run
```

**출력에서 정리 후보가 0개라면 실제 삭제를 실행할 이유가 없습니다.** 결과에는 예상 처리량, 보호 조건, 실행 시 자원 영향을 함께 기록합니다. `--prune-profiles`는 아바타·헤더에 영향을 주는 **별도** 작업이므로 기본 명령에 붙이지 않습니다.

운영 버전에서 `--keep-interacted`가 지원되는 경우, 상호작용한 원격 미디어를 보존하도록 Dry Run과 실제 실행에 **같은 보호 옵션**을 사용할 수 있습니다. 이 옵션은 일부 버전·커스텀 빌드에만 존재할 수 있으므로 공식 문서에 없다고 해서 보편적으로 지원된다고 가정하지 마세요.

```bash
# 현재 실행 버전에서 --keep-interacted 지원을 확인한 경우에만
docker compose exec -T web bin/tootctl media remove \
  --days 30 --keep-interacted --concurrency 2 --dry-run
```

Dry Run 결과와 운영 정책을 검토한 뒤, 실제 삭제 필요성이 있을 때만 `--dry-run`을 제외하고 실행합니다. 대량 작업은 먼저 보존할 데이터를 확인하고, 다른 정리 작업과 겹치지 않도록 계획합니다.

## 2. S3 호환 저장소와 R2를 쓴다면

DB의 **미디어 경로와 실제 객체 키**, 버킷 이름, S3 endpoint, 공개 미디어 도메인을 각각 구분해야 합니다. 특히 과거에 버킷 이름을 경로에 포함했던 구성을 변경할 때에는 기존 키와 새 키가 섞일 수 있습니다.

- 설정을 변경하는 것만으로 기존 객체가 자동 이동하지 않습니다.
- 경로 문제와 객체 자체의 유실을 구분합니다. 새·옛 경로 모두에서 찾지 못한 객체는 복구 가능성이 별도로 확인돼야 합니다.
- DB가 참조하는 경로를 보호하지 않는 **버킷 전체 일괄 삭제는 피합니다**.
- 객체 목록 조회, Head/GET, 삭제 요청은 R2 사용량과 API 비용에 영향을 줄 수 있습니다. 표본 검사만으로 전체 DB–스토리지 정합성을 증명할 수는 없습니다.

이런 마이그레이션·레거시 객체 조사에는 범용 삭제 스크립트를 바로 적용하기보다, 현재 운영 환경의 객체 경로와 보호 조건을 문서화한 **별도의 작업 계획**이 필요합니다.

## 3. 정기 유지보수가 꼭 필요한가?

캐시 증가가 운영 비용·저장 공간에 영향을 주고 정책이 명확하다면 `systemd` timer 등을 이용해 정기 실행할 수 있습니다. 다만 운영 규모가 작거나 Dry Run 후보가 계속 0개라면 **자동 삭제를 필수로 볼 필요는 없습니다**.

정기화할 때는 다음을 구분합니다.

- 정리 작업의 **성공·실패와 실행 누락** 감시
- 실제 서비스 **HTTP 가용성** 감시 — [웹사이트 모니터링](uptime-monitoring.md) 참고
- 작업 중복 방지, 동시 처리량 제한, 로그 확인

자동 정리의 성공은 **전체 미디어 저장소 무결성 검증 성공**이 아닙니다. 백업과 복원 계획은 [백업 체크리스트](backup-readiness.md)를 따릅니다.

## 운영 사례 메모: 남은 객체는 모두 삭제 대상인가? (2026-11-16, 1차 기록)

머스타드의 과거 R2 중첩 경로를 정리한 뒤에도 여섯 개 레거시 미디어 접두사에 **73,071개, 약 14.601 GiB**가 남아 있었습니다(기존 백업 파일 제외). 첨부파일 정리 로그의 `no_copy=30,867` 및 `mismatch=82` 합계는 해당 접두사의 잔여 객체 **30,949개**와 일치했지만, 이는 개별 객체의 동일성을 완전히 증명하지는 않습니다. 소량의 DB 참조 표본에서는 현재 미디어 레코드가 발견되었고, 그중 세 객체는 정상 경로에도 같은 크기로 존재했습니다.

따라서 **정리 완료의 기준을 잔여 객체 0개로 두지 않고**, 정상 사본 부재·메타데이터 불일치·현재 DB 참조 가능성 때문에 남은 객체를 보존하기로 했습니다. 작은 표본 검사, 객체 크기 일치, DB 레코드 부재 중 어느 하나만으로 전체 삭제를 허가하지 않는다는 교훈입니다. 이미 검증된 정리 배치를 무조건 반복할 이유도 없습니다.
